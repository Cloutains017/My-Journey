# 网站数据保护方案与执行记录

日期：2026-09-22。目标：降低后台被攻破的概率，并使管理员会话失窃后的删除可恢复。

## 方案

1. 登录：数据库原子计数限速，同一来源每 15 分钟最多 10 次尝试，全站每 15 分钟最多 100 次。包括成功尝试，避免并发绕过；存储不可用时拒绝登录。Vercel 托管时只信任平台覆盖的来源头，其他环境归入共享桶。来源保存为 HMAC 摘要。
2. 请求：后台写操作校验同源 Origin，拒绝跨站 Fetch Metadata。安全 Cookie 继续使用签名、HttpOnly、Secure、SameSite=Strict。新增退出登录入口。
3. 删除：通过数据库事务先保存完整快照再删除展示记录。旅程快照包含照片及两类评论；照片移除时清理指向该照片的封面。不再调用 R2 删除接口。回收站仅管理员可读和恢复，不提供清空入口，不自动过期。保留空间会增加，后续清理由站点所有者离线决定。
4. 恢复：在同一事务中恢复原 UUID 及关联数据；冲突时整体失败，不覆盖现有记录；恢复照片时只补回仍为空的原封面。
5. 审计：业务表新增、更新和删除由数据库触发器记录。修改前后内容保留，便于追踪和离线修复恶意篡改；登录结果另行记录，不记录密码、Cookie、密钥。审计表及回收站开启 RLS，仅服务端可访问。
6. 上传：服务端生成不可预测的新对象路径，不允许客户端选择旧对象路径覆盖原图；只允许常见图片类型。注册时确认对象真实存在且属于对应旅程。
7. 权限：核查线上 RLS 和授权；对业务表撤销匿名/普通登录用户的写权限，保留公开读取。RPC 使用 SECURITY INVOKER，撤销 PUBLIC/anon/authenticated 执行权，只授权 service_role。
8. 备份：提供本地独立导出工具，保存业务表、回收站、审计记录以及 R2 对象，附 SHA-256 校验清单；输出目录不进入 Git。备份凭据仅在本机读取。备份是逐表/逐对象导出，不是数据库一致性快照。

## 实施结果与限制

Supabase 已重新连接，线上迁移 `admin_security_recovery_and_audit` 已成功应用。实际核查确认 city_boundaries 原本已启用 RLS；这次修复本地建表脚本，并撤销线上业务表的匿名及普通登录角色写入/清表授权。

所有 8 张 public 表启用 RLS，3 张后台安全表对访客完全不可读写；4 个管理员函数只有 service_role 可执行且均为 SECURITY INVOKER。Supabase Advisor 无 WARNING/ERROR，3 条 INFO 提示安全表无 RLS policy，属于刻意默认拒绝设计，不应为消除提示添加公开策略。说明：https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy 。

最新本地快照：`backups/2026-09-21T19-13-35-566Z`；包含 52 条旅程、1,015 条照片记录、8 条认可度评论、3 条心动指数评论、22 条动态城市边界和 1,114 个 R2 对象。所有文件校验和通过，并在内存 PostgreSQL 恢复业务表验证计数与外键约束。

网站回收站能恢复删除内容，审计快照支持所有者离线分析修改内容；暂不提供任意版本一键回滚。备份工具和恢复演练已实现，本轮完成即时备份。

网站回收站和审计不能抵御 service_role 或平台账号失窃。数据库登录限速有全局拒绝服务权衡，也不承担 DDoS 防护。

## 应急操作

先暂停后台写操作并保存日志；更新 ADMIN_PASSWORD，若配置了 ADMIN_SESSION_SECRET 则同步轮换，重新部署使旧会话失效。按泄漏范围轮换服务端密钥，验证新凭据后撤销旧凭据。先在隔离环境恢复备份、核对旅程/照片关联，再恢复正式站点。回滚应用版本不能恢复已删除的数据，也不能撤销数据库迁移。
